# タグを閲覧サイトにも出し、各一覧の絞り込みに使う

## Context

ADR-0036 でタグは管理用とし、読者には見せないと決めた

付いているタグはコラボ、タイアップ先、シリーズなど、読者にとっても意味のある観点だった

閲覧サイトの楽曲・イベント・リリース一覧には、種別とテキストで絞り込む `FilterBar` がすでにある

検討した案は次のとおり

- タグごとに公開可否を持つ: 管理用の内部タグを残せるが、そうした用途が今のところ無く、Tag のフィールドが増える
- 公開用の別概念 (シリーズなど) を新しく作る: 同じ観点を 2 つの概念で二重に管理することになる
- タグページ (`/tags/[tagId]`) で対象をまたいで一覧する: 横断分類を活かせるが、新しい画面と導線が要る
- サイト全体の横断キーワード検索: 面積が大きく、今回の要望に対して過剰

## Decision

- ADR-0036 の「タグは管理用とし、読者には見せない」を置き換え、すべてのタグを閲覧サイトにも出す。タグごとの公開可否は持たない
- Viewer API は楽曲・イベント・リリースグループの一覧 item に `tags` (`tagId` / `name` / `orderNo`) を、タグの表示順で埋め込む。`orderNo` は一覧のセレクトの選択肢を並べるために使う。タグ専用の Viewer エンドポイントは作らない (ADR-0021)
- 閲覧サイトは楽曲・イベント・リリースの詳細にタグを出し、一覧の行には出さない
- 楽曲・イベント・リリースの各一覧で、タグのセレクトとテキスト検索の両方で絞り込めるようにする
  - セレクトの選択肢は、その一覧の公開中の記録に付いたタグだけにする
  - 選んだタグは `?tag=<tagId>` と同期し、詳細のタグから同じ種類の一覧へこのクエリ付きで飛べるようにする
- メディアは閲覧サイトに一覧が無いので、タグを出さない

## Consequences

### Positive

- 読者が、コラボやシリーズの観点で楽曲・イベント・リリースをたどれる
- 既存の一覧と `FilterBar` の延長で済み、新しい画面を持たない
- 一覧 item に埋め込むので、SSG のビルド時取得の回数が増えない

### Negative

- タグ名の変更がそのまま閲覧サイトに出るので、管理者は読者に見せる前提でタグを名付ける必要がある
- 対象をまたいで 1 つのタグの記録をまとめて見る画面は無い
- 非公開の記録にしか付いていないタグは、どの一覧の選択肢にも出ない
