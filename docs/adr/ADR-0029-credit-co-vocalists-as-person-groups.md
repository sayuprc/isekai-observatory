# 共演者は人単位で保存し出演グループは共演者ごとの任意参照で表す

## Context

V.W.P のように同じ顔ぶれで歌う共演が多く、楽曲披露ごとに人物を 1 人ずつ追加するのは手間がかかる
Viewer でも人数の多い共演者は個人名を並べず、グループ名で安定して表示したい

一方で共演者は人単位で辿れる必要がある
グループ参照だけを保存すると、加入・卒業や一部メンバーだけの披露を表現できない
表示時にグループの現在のメンバー構成と突き合わせて推定すると、構成の変更で過去の表示が変わる

## Decision

- 人物グループ `PersonGroup` を Person 文脈のマスタとして持つ。管理用名称 (一意)、表示用名称 (重複可)、順序付きのメンバーだけを持ち、所属期間は持たない
- メンバーの一時離脱は、離脱パターンごとに別のグループ (例: `グループA (B不在)`) を作って表す。表示用名称を揃えれば Viewer では同じ名前で見える
- 楽曲披露の共演者は従来どおり Person 単位で保存し、各共演者に任意の出演グループ `personGroupId` を持たせる
- 出演グループ付きの共演者は、そのグループとして全員で出演したことを表す。一部メンバーだけの披露は個人として記録する
- 出演グループ付きの共演者とグループの現在のメンバー構成が一致するかは検証しない
- Viewer は出演グループ付きの共演者をグループの表示用名称 1 つにまとめて表示する。まとめる処理は Viewer 用の read model で行う。Admin は管理用名称で見分ける
- Person を削除するとグループの所属は外れる。楽曲披露から参照中のグループは削除できない
- 管理導線は `/person-groups` とする。ADR-0023 の `/persons` 一本化は人物マスタの二重登録を防ぐもので、別マスタのグループとは衝突しない

## Consequences

### Positive

- グループを選ぶだけで共演者を一括入力でき、人単位の参照も残る
- メンバー構成を変えても過去の楽曲披露の記録と表示は変わらない
- 一時離脱してもマスタのメンバーを外して戻す必要がなく、離脱していた回はその人の共演記録に残らない

### Negative

- グループの表示用名称を変更すると過去の楽曲披露の表示名も変わる
- 離脱の組み合わせが増えると、グループの数も増える
- 一致を検証しないため、出演グループ付きで一部の人だけを残すデータは運用で避ける必要がある
