# 一括操作は対象ごとの API で、全部成功か全部失敗とし、監査ログは記録ごとに残す

## Context

タグの付与や表示・非表示の切り替えを、記録ごとに編集画面を開いて行うと手間が大きい

タグ付けは付けられる側の集約が持つ (ADR-0036) ので、一括操作は楽曲、イベント、リリースグループ、メディアの複数のパッケージにまたがる

検討した案は次のとおり

- `target_type` を受ける横断的な 1 本の API: 画面と契約は単純だが、1 つの UseCase が複数パッケージの集約に依存する
- 成功した分だけ反映し、失敗した記録を返す: 件数が多いときに進めやすいが、状態が割れてやり直しが複雑になる

## Decision

- 一括操作の API は対象ごとに持つ (`/songs/bulk`、`/events/bulk`、`/release-groups/bulk`、`/media/bulk`)
- 操作は、タグの付与、タグの除去、表示・非表示の切り替えを 1 リクエストで組み合わせて指定でき、少なくとも 1 つは指定する
- 同じタグを付与と除去の両方に指定することはできない
- 1 トランザクションで処理し、1 件でも失敗したらどの記録も変更しない
- 付与済みのタグの付与や、付いていないタグの除去は何もせず成功とする
- 付与するタグが存在しないときは 400 とする
- 監査ログは変更した記録ごとに 1 件残す (ADR-0022)。値は更新後の集約の `toArray()` とする
- 権限は対象ごとの Write 権限を使う
- 1 リクエストで受け付ける件数に上限を設け、値は契約に書く
- 削除の一括実行と、検索条件に一致する全件を対象にする指定は扱わない

## Consequences

### Positive

- パッケージ境界を保ったまま、各集約の既存の保存処理と監査ログを再利用できる
- 失敗しても状態が割れず、やり直しが単純になる
- 各記録の履歴タブに、一括操作による変更が通常の更新と同じ形で出る

### Negative

- 対象を増やすたびに、契約、UseCase、コントローラーを足す必要がある
- 件数が多いと 1 トランザクションが長くなるため、件数の上限が必要になる
- 1 件の失敗で全体がやり直しになる
