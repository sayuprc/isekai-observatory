# 管理画面の詳細・作成画面は固定見出しと保存操作、セクションの多い画面はタブで構成する

## Context

管理画面の詳細・作成画面は、すべてのセクションを縦に積み、更新ボタンと「危険な操作」の枠を画面の最下部に置いていた。イベントのように楽曲披露やセットリストを持つ画面では、保存するたびに最下部までスクロールする必要があった

未保存のまま画面を離れても警告がなく、作成と編集で入力状態や入力欄の実装が重複していた

リデザインでは、実画面での比較を経て、配色とフォントも見直した

## Decision

- 詳細・作成画面の上部に `EntityHeader` を置き、パンくず・タイトル・状態のチップ・未保存表示・破棄・保存・操作メニューを持たせる
  - sm 以上は Layout のヘッダー直下に固定する
  - sm 未満は見出しを固定せず、保存操作だけを画面下に固定する
- 削除など頻度の低い操作は、操作メニュー (`ActionMenu`) に置く。「危険な操作」の枠は使わない
  - 削除できない条件の注意書きは、関連する一覧の枠など、条件が見える場所に出す
- 未保存の変更は、件数ではなく有無だけを示し、未保存のまま離脱しようとしたらブラウザの確認を出す
  - 比べる基準は、表示が終わった時点の値にする
  - 保存する値が元に戻れば、変更なしに戻る
- セクションが多い画面 (イベント・楽曲・リリース) はタブで分ける
  - 表示中のタブは URL の `?tab=` に同期し、非表示のタブも DOM に残して入力途中の状態を保つ
  - 詳細画面には履歴タブを置き、監査ログを対象の種別と ID で絞って出す
- 入力欄はラベルを左に置く行 (`FormRow`) で並べ、選択肢が少ない単一選択は選択肢ボタン (`SegmentedControl`) にする
- 作成と編集で同じ入力を持つ画面は、入力状態 (`create*Form`) と入力欄 (`*FormFields` など) を共通化する
- テーマは DaisyUI の `dim`、フォントは既定のものを使う

## Consequences

### Positive

- 保存操作が常に見え、長い画面でも保存のためにスクロールしなくてよい
- 未保存の変更を失いにくくなる
- タブにより、演目の入力など広さが要る作業を 1 画面で行える
- 作成と編集の入力が共通化され、片方だけ直し忘れることが減る

### Negative

- タブで隠れた入力欄の検証エラーに気付きにくい。ブラウザの検証で弾かれた欄はタブを開き直すが、サーバーの検証エラーはタブを切り替えない
- 未保存検知は保存する値全体を毎回比べるので、入力量の多い画面では比較の負荷がかかる
- 固定見出しの高さを前提にした `top-*` の指定があり、見出しの構成を変えるときは追従が要る
