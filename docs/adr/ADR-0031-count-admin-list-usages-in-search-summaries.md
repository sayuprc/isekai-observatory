# 管理画面の一覧の件数は検索用の Summary 型で返し、Application 層のクエリで数える

## Context

管理画面の一覧からは、楽曲披露やセットリストが未入力のイベントなど、入力待ちの記録を見つけにくかった

一覧の検索 API には、詳細取得や他画面と同じ型をそのまま返しているものがあった (Media・Person・PersonGroup・Venue・SongTag)

件数は記録の性質ではなく、他の記録からどれだけ参照されているかという読み取り専用の値である

## Decision

- 一覧の表に件数の列を足し、件数は検索 API のレスポンスに含める
- 詳細取得などで共有している型は変えず、検索用に件数を持つ `*Summary` 型を定義する
- 件数はドメインのモデルに持たせず、Application 層のクエリサービス (`*UsageCountQueryServiceInterface` など) で引く
  - 実装は Infrastructures に置き、1 ページ分の ID をまとめて `QueryFactory::countBy` で数える。行ごとの問い合わせは行わない
- 件数は重複を除いて数える
  - 1 曲で作詞と作曲を兼ねる人物は、楽曲 1 件と数える
  - 版をまたいで収録された楽曲は、1 曲と数える
  - グループのメンバーが何人入っていても、楽曲披露 1 件と数える
- 一覧には新しい絞り込みを足さない。絞り込みは既存の検索条件のままにする
- 一覧に選択中の行のプレビューは置かない

## Consequences

### Positive

- 入力待ちの記録や参照されていない記録を、一覧から見つけられる
- 詳細取得の型や他画面に影響を与えずに、一覧だけに項目を足せる
- 件数の取得がドメインのモデルに混ざらない

### Negative

- 一覧の 1 ページごとに、件数の種類だけ問い合わせが増える
- 検索用の `*Summary` 型と元の型で、同じ項目を二重に定義する
- Arkitect の設定で、Application 層のクエリを持たなかった Venue に `Query` コンポーネントを足す必要があった
