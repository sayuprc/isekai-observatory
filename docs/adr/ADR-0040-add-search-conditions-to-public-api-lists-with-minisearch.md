# Public API の一覧に検索条件を足し、MiniSearch の索引を静的ファイルで配信する

## Context

ADR-0038 は検索を「需要が見えてから D1 などを使う別の口として追加する」と先送りした

検索がない間は、利用者が全ページを取得して手元で絞り込む必要がある

検討した方法は次の 3 つ

- MiniSearch で deploy 時に索引を作り、静的ファイルとして Worker から読む
- deploy 時に Cloudflare D1 へ投入し、SQL で検索する
- R2 に分割した索引を置き、Worker が必要な分だけ読む

データは現在約 1,800 件で、検索対象のテキストは約 59,000 文字

MiniSearch の索引は全リソースを合わせても 359KB (gzip 99KB) で、ローカルでは初回 約 32ms、2 回目以降は数 ms で応答した

D1 は検索に十分だが、スナップショットに加えて投入の仕組みと費用が増える

R2 の分割索引は検索エンジン相当を自作することになる

## Decision

- 検索は別のエンドポイントを設けず、各一覧 (`/v1/songs` など) のクエリパラメータで行う
  - 横断検索は提供しない
  - 検索結果にも `pageSize` / `pageToken` を使える
- 全文検索はフィールドを指定したパラメータだけに対応する
  - 対象は `title` / `name` / `songTitle` とし、一覧ごとに指定できるものが異なる
  - `q` による全フィールド検索と、説明文の検索は提供しない
  - 空白区切りの語をすべて含むものに絞る
  - 日本語は CJK を 2 文字ずつに分けて索引化する
- 完全一致の絞り込みは `type` / `status` / `kind` に対応する
  - カンマ区切りで複数指定すると、いずれかに一致するものに絞る
- 複数のパラメータを指定したときは、すべてを満たすものに絞る
- 並び順は、全文検索の条件があれば関連度の高い順とし、絞り込みだけなら通常の並び順とする
  - 関連度の計算は契約で保証しない
  - `pageToken` は検索結果内の位置を表すが、中身は契約で保証しない
- 絞り込みの値が存在しない値でも、エラーにせず 0 件を返す
  - 契約に無いパラメータ名は無視する
  - 入力形式の検証は契約 (OAS) を単一の情報源とする (ADR-0014)
- 索引は `viewer-deploy` の `snapshot` で、リソースごとの静的ファイル (`/search/{resource}.json`) として書き出す
  - Worker は一覧を要求されたリソースの索引だけを、isolate ごとに 1 回だけ読み込んで保持する
  - 検索条件が無いリクエストは、索引を読まずに従来どおり一覧を返す
- 索引が Worker の起動時間・メモリ・CPU 時間の制限に近づいたら、D1 などへ移す
  - 移行しても、クエリパラメータの契約は変えない

## Consequences

### Positive

- 利用者は全ページを取得せずに、タイトルや種別で絞り込める
- API サーバーと DB への問い合わせは増えない
- 索引の仕組みがスナップショットと同じ build に収まる
- 検索条件をクエリパラメータにしたので、配信方法を D1 などへ移しても契約を壊さない

### Negative

- 索引の大きさはデータ量に比例する。ADR-0038 の「データ量に関わらず 1 リクエストの読み取り量が一定」は、検索については成り立たない
- 初回リクエストは、索引の取得と復元の分だけ遅い
- 検索結果が複数のチャンクに散らばると、1 リクエストで最大 100 ファイルを読む。Free プランのサブリクエスト上限に当たる恐れがある
- Free プランでの起動時の CPU 時間は、デプロイして測るまで確認できていない
- 絞り込みの値を間違えても 0 件が返るだけで、利用者が誤りに気づきにくい
- 日本語を 2 文字ずつで引くので、1 文字の語は 1 文字として一致を見る。表記ゆれや読みの違いは吸収できない
- 関連度の順位は MiniSearch の実装に依存する
